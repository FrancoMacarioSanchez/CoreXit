PARTE II: ANEXO I — ACUERDO DE NIVEL DE SERVICIO (SLA) Y POLÍTICA DE USO ACEPTABLE DE API

El presente Anexo forma parte integrante de los Términos y Condiciones Generales y regula los estándares técnicos de disponibilidad, soporte y consumo de la API de facturación.

1. COMPROMISO DE DISPONIBILIDAD (UPTIME)

1.1. Disponibilidad Mensual: El PROVEEDOR realizará sus mejores esfuerzos técnicos para asegurar una disponibilidad operativa de la Plataforma y del Microservicio de API del 99,0% (noventa y nueve por ciento) medido de forma mensual.

1.2. Exclusiones del Cálculo de Uptime: No se computarán como tiempo de inactividad (Downtime) las interrupciones originadas por:

  • a) Ventanas de mantenimiento programado notificadas con al menos veinticuatro (24) horas de antelación (preferentemente en horario nocturno entre las 00:00 y las 06:00 hs ART).
  • b) Caídas, lentitud, errores HTTP 500/502/503/504 o mantenimientos propios de los servidores y Web Services de ARCA (wsaa, wsfev1, etc.).
  • c) Suspensiones de cuenta por mora o por violación de los límites de consumo (Rate Limiting).
  • d) Problemas de conectividad local del CLIENTE o errores de integración en el código desarrollado por el propio CLIENTE.

2. POLÍTICA DE USO JUSTO Y LÍMITES DE CONSUMO DE API (RATE LIMITING)

2.1. Cuotas de Peticiones: A fin de proteger la estabilidad de la arquitectura multi-inquilino (multi-tenant) y evitar bloqueos de IP por parte de ARCA, el consumo de la API está sujeto a límites de velocidad (Rate Limits) según el plan contratado (por ejemplo, un máximo de [EJ: 60] peticiones por minuto por entorno/CUIT).

2.2. Prohibición de Abuso de WSAA: Queda prohibido que los sistemas del CLIENTE fuercen la solicitud de nuevos Tickets de Acceso (TA) ante ARCA en cada petición individual; el CLIENTE debe respetar la gestión automatizada de caché de tokens implementada por el PROVEEDOR.

2.3. Medidas de Mitigación: Ante picos de tráfico anómalos, bucles infinitos (infinite loops) en el software del CLIENTE o intentos de saturación, el Sistema devolverá respuestas HTTP 429 (Too Many Requests) y el PROVEEDOR podrá bloquear preventivamente el token de API o la dirección IP de origen hasta que el CLIENTE corrija el desperfecto técnico.

1.1. Datos del propio CLIENTE: Respecto de los datos de registro y facturación del CLIENTE que contrata el SaaS (nombre o razón social, CUIT, domicilio fiscal, teléfono, correo electrónico e historial de pagos del abono), el PROVEEDOR actúa como Responsable de la Base de Datos.

Datos de Terceros cargados por el CLIENTE (Prestación de Servicios Informatizados - Art. 25 Ley 25.326): Respecto de los datos personales, comerciales y tributarios que el CLIENTE ingresa en la Plataforma o envía a través de la API para emitir facturas (datos de los compradores o consumidores del CLIENTE, tales como nombres, DNI/CUIT, domicilios, correos electrónicos y detalle de compras), el CLIENTE es el único Titular y Responsable de la Base de Datos, mientras que el PROVEEDOR actúa estrictamente como "Encargado del Tratamiento" (prestador de servicios de tratamiento de datos por cuenta de terceros, conforme al artículo 25 de la Ley N° 25.326).
